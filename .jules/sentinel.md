## 2024-05-24 - [IDOR in Post Creation and Missing Route Authentication]
**Vulnerability:** The `POST /api/posts` and `POST /api/posts/:id/react` endpoints lacked authentication middleware in the routes definition. Furthermore, the `createPost` controller implicitly trusted `req.body.userId`, allowing any user to potentially create posts masquerading as someone else (IDOR).
**Learning:** Controller logic alone is insufficient if the middleware protecting it is missing from the route. User-supplied identification data (like `userId` in the body) should never be trusted for actions linked to the authenticated user.
**Prevention:** Always verify that routes defining state-changing endpoints (POST, PUT, DELETE) have authentication middleware applied. Within controllers, always rely on `req.user.id` (set by the authentication middleware) to determine the user performing the action, rather than relying on the client to send a `userId`.
## 2024-05-24 - [Broken Authentication due to mismatched JWT payload key]
**Vulnerability:** The authentication middleware (`authenticateToken` and `optionalAuth`) attempted to extract `decoded.userId` from the verified JWT token. However, the token generation logic (`auth.service.js`) signed the payload with `{ id }`. This mismatch resulted in `userId` being `undefined` during verification, causing `User.findByPk(undefined)` to consistently return `null` and subsequently fail all authentication checks with a 401 "User not found" error, effectively locking out valid users.
**Learning:** Hardcoded payload structures in distributed services (e.g., generation in services vs extraction in middleware) can easily drift, breaking fundamental security flows like authentication.
**Prevention:** Standardize the expected keys within JWT payloads across the codebase. Consider defining a shared interface or constant for payload keys to ensure both the signing and verifying components rely on the same structure. Ensure robust testing around protected endpoints with realistic token generation.
